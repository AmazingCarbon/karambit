Your agents get to use secrets, not see them.

How Karambit lets Claude Code, Codex, pi and friends run your tests, deploys and AWS commands with real credentials, while the secret values stay out of the agent's context, transcript and logs. With the parts it does not do, stated plainly.

What it does

Keeps values out of the agent's own process and context window, asks for your fingerprint where you want it, binds each use to one command, redacts output, and logs who used what.

What it doesn't

It is not a sandbox. A program the agent launches with a secret does get that secret. A determined agent can make that program leak it. Karambit makes that hard, slow and loud, not impossible.

Where secrets live when nobody is using them

Three places, three jobs. The disk holds only ciphertext. The keys that open it never leave a chip in your Mac. Unlocked values exist only briefly, in one process's memory.

What happens when an agent needs a secret

The agent never asks for the value. It asks Karambit to run a program with the secret attached. Here is one run, start to finish.

"Can't the agent just keep a copy?"

Directly, no. Through the program it launches, yes, if it really tries. That's the honest answer, and it's why the controls below exist.

Agent

karambit get stripe/live-key

Karambit

Refused: revealing a secret is human-only, and your process chain includes an agent (claude). Use the app or a plain terminal.

Agent, getting creative

karambit run -e X=stripe/live-key -- sh -c 'echo $X > /tmp/x'

Karambit

That would work for an Agents · no prompt secret, and I'd log it. For this one you set Only me, so: refused. For Touch ID secrets, your human gets a fingerprint prompt naming the exact command.

Blocked for agents

  • Reading values: get, reveal, copy to clipboard
  • Decrypting the vault files (keys are in the chip)
  • Reading the daemon's memory (macOS SIP refuses it, tested)
  • Granting itself leases, relaxing access, adding or deleting secrets
  • Using Only me secrets at all
  • Faking a Touch ID press

Still possible

  • A launched program writing the value to a file or sending it over the network (redaction only covers screen output)
  • Another program running as you reading that program's environment while it runs (ps -E)
  • A process that double-forks and wipes its environment can look human to detection; Touch ID is the real backstop

What keeps that in check

Touch ID per use

For sensitive secrets an agent must wait for your finger, and the prompt names the command.

Narrow leases

Temporary access you grant for one command, one folder, a few uses, a few hours.

--jail

Experimental macOS sandbox: no network except allowed local ports, most files off-limits.

Audit + block

Every use is logged with agent, session and command. karambit block refuses all agents at once.

"Won't AWS break if requests go through Karambit?"

They don't go through Karambit. Karambit uses the credential mechanism every AWS SDK and the AWS CLI already support for containers: the SDK asks a local address for temporary keys, then talks to AWS by itself.

aws s3 ls (the SDK inside it)

My environment says credentials are at http://127.0.0.1:52811/… with a token. Fetching.

Karambit

Token matches this run. Here are role keys from your SSO sign-in, valid until 14:05. Come back before then.

AWS

Signed request from the SDK, straight to me. Here's your bucket list. Nothing in between.

Works like normal

  • AWS CLI, boto3, the Go/JS/Java SDKs, Terraform, kubectl
  • Long jobs: SSO role keys are refreshed for the whole sign-in
  • Uploads, streaming, paging, retries: requests aren't touched
  • Signed out? The next fetch fails with a clear "sign in to <portal>" message

Can trip it up

  • Tools that parse ~/.aws/credentials themselves instead of using an SDK
  • Very old SDKs without container-credential support
  • Handing the job to a separate container without passing these two variables
  • The temporary keys are visible to the program until they expire (15 min for pasted keys)

Your existing .env files

Agents read .env files constantly, and paste them into prompts and commits. karambit secure (or karambit eat) moves them into the vault in one go, and npm run dev keeps working.

Preview

karambit secure --dry-run lists variable names only, guesses which are secret, warns if the file was ever in git.

Store

One Touch ID. Each secret becomes myapp/STRIPE_KEY; the original file is archived whole.

Replace

A value-free .env.schema is written and trusted. The plaintext .env is deleted after the archive is verified.

Work as usual

Scripts get a karambit run -- prefix. karambit secure rebuild puts the old files back exactly.

# .env.schema: safe to commit, holds no secret values (varlock @env-spec format)
# ---
PORT=3000
APP_URL=http://localhost:${PORT}
# @sensitive
STRIPE_KEY=karambit(myapp/STRIPE_KEY)
Agent

Let me check the config. cat .env.schema

Karambit

Read away: it's names, plain settings and references. The values are in the vault. And if you edit the schema to point at other secrets, I'll refuse it until your human trusts it again with Touch ID.

More questions people ask

Can't the agent just pretend to be me?

Detection reads the process tree and environment markers from the kernel, never from what the caller says. A process that double-forks and scrubs its environment can look human; that's documented. The hard backstop is Touch ID: Only me and Touch ID secrets need a physical fingerprint, enforced by the Secure Enclave, not by Karambit's code.

Why not just use the macOS Keychain?

Keychain items are protected in software by your login password, and access rules depend on code signatures that change on every rebuild. Karambit's keys are hardware-bound in the Secure Enclave, with a separate key per access level. Keychain would add a second copy, not more protection.

What about the clipboard?

Copy is a human action. The value is marked as concealed and cleared after a short timer, but any program running as you can read the clipboard until then.

Are unlocked secrets protected in RAM?

They live only in the daemon's memory, and macOS refuses same-user debugger attach to it. Locking that memory against swap, disabling core dumps and denying attach outright are not done yet; they're next on the hardening list.

Does it work on Linux or Windows?

The core builds on Linux, but the security parts (hardware keys, caller identity, bound launch) are macOS only today. Elsewhere Karambit refuses rather than pretending.

Is varlock involved?

Karambit reads the same .env.schema format as varlock (@env-spec), ported to Rust from their MIT-licensed parser and tested against it (48 of 48 parse cases match). Varlock's plugin functions like op() or exec() are refused, so a schema never runs a command. Credit and license: THIRD_PARTY_NOTICES.md.
